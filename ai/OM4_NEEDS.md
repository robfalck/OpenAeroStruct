# om4 needs found while porting OpenAeroStruct

Running list of om4 components, features, and bugs that the OAS port ran into.
Each entry says what OAS does about it in the meantime. Strike through (`~~...~~`)
when resolved upstream; don't delete. ✅ = fixed on om4 `main`; 🟡 = fixed on an om4 branch that isn't merged to `main` yet. Unmarked = still open.

**Last reassessed 2026-10-06 against om4 `upstream/main` @ `0787fcbf`**, by rerunning every repro in `ai/tools/repros/` and the original probes against a clean worktree of that commit. Minimal reproductions live in `ai/tools/repros/`.

| N-001 | `SplineComp` (at least `method="bsplines"`; OM3 also has akima, scipy methods) | `geometry/geometry_group.py`, structures groups (twist/chord/shear/thickness control points) | OAS-local `openaerostruct/utils/bspline_comp.py:BsplineComp`, a verbatim port of OM3's B-spline basis. | N-002 | Per-subjac approximation (OM3 `declare_partials(of, wrt, method="cs"/"fd")`). `PartialsSpec` has no `method`; only a component-wide `differentiator` | ~16 components. | N-003 | `assert_check_partials` and other testing asserts | every partials unit test | `openaerostruct/utils/testing.py:assert_check_partials` |
| N-004 | Per-component check settings (OM3 `set_check_partial_options(wrt, method, step)`) | ~17 components declare FD steps or CS for checking | Dropped from components. Tests pass the differentiator/step to `run_test` |

| 🟡 N-006 | Total coloring is computed once and isn't cached per of/wrt layout. Changing the request recomputes it, logging the misleading "Pre-computed coloring … is not compatible … will be computed dynamically" even though om4 computed it, not the user. An optimizer that interleaves a second request (e.g. a diagnostic `compute_totals`) recomputes coloring each time it switches. Options: key colorings by layout, or reword the warning **Fixed in om4 `3c6068e9` on branch `compute_totals_layout_bug` (per-layout coloring cache, last 4 layouts); not on `main`.** | Reported by the om4 session while fixing B-007 | none needed yet; OAS doesn't use total coloring so far |
| N-007 | `ExecComp` has no diagonal-partials option (OM3 `has_diag_partials`). Vectorized ExecComps declare dense partials, so total and partial coloring can't help them | Reported by the om4 session while fixing B-007 | OAS uses few ExecComps; revisit when porting the ones in `integration/` |

## Bugs / behavior differences

| ID | Issue | Evidence | Interim in OAS |
|---|---|---|---|
| B-001 | `check_partials` builds the FD/CS reference **only inside the declared sparsity pattern** (`compexecnode.py:436`, `subjacs = {n: sj.copy(zero=True) ...}`), so undeclared nonzeros and undeclared `(of, wrt)` pairs are invisible. OM3 compares against a dense approximation | Probe: `y = x**2 + x[0]` with only a diagonal declared; `Jref` showed zeros in column 0 below the diagonal | `utils/testing.py:assert_sparsity_complete` does a dense FD sweep for small explicit components. Ports are also cross-checked against OM3's analytic Jacobians **om4 session's estimate (2026-10-06): moderately cheap, confined to `check_partials`/`compare_jacs` (dense reference for every `(of, wrt)`, missing analytic pairs as zeros, reference run without partial coloring); costs a full uncolored FD/CS per check. Awaiting Robert's decision.** |
| B-002 | `get_tol_violation` returns `(0.0, 0.0, False)` for empty arrays, but callers unpack `(above_tol, max_abs, max_rel)`, so the order is wrong. Harmless today, since `0.0` is falsy | `om4/utils/array_utils.py:541` | none |
| 🟡 B-003 | **Duplicate `(row, col)` entries in a sparse pattern give wrong numbers outside the analytic matvec path.** First found as a false `check_partials` failure: the FD/CS reference counted a repeated coordinate once per listing (`Jref` 6 where 3 is correct). The om4 session's audit found the root cause in `COOSubmat` (`set_val_from_dense`, `set_col`, `set_row` wrote the full value into every listing) plus a second bug in `copy_to` (last listing wins). Real wrong answers: **CS as a component's differentiator** doubled totals (fwd and rev); FD did too under a sparse-assembled `DirectSolver`; partial coloring with FD/CS likewise; and **analytic partials under `DirectSolver(assembled_format="dense")`** were wrong (2.5 vs 4.2857 in a Newton/Direct cycle). Unaffected: matvec, `todense`, sparse assembly of analytic partials, group-level FD/CS, second-order checks, JAX/asdex. **Fixed on om4 branch `check_partials_duplicates` (from `main` `f21a3f5f`), uncommitted as of 2026-10-06; fix confined to `om4/derivatives/submat.py`, tests in `om4/derivatives/tests/test_duplicate_partials.py`.** | `ai/tools/repros/check_partials_duplicate_entries.py`: `J[0,0]=3` (correct), `Jref[0,0]=6`; fwd/rev totals both 3. Fixed branch prints `Jref` `[3, 1, 1]`, not reported wrong | **Correction:** an earlier version of this entry claimed OAS keeps duplicate patterns (`Stretch`, `Sweep`, `Dihedral`, …). A scan of all 28 ported components in 3 configurations (2026-10-06) found **no duplicate entries**, so OAS hasn't hit this. Re-scan when porting structures and the coupled groups, which will use `DirectSolver` |
| ✅ B-004 | **Silent unit error.** An unconnected promoted input whose leaves declare different units, set with `Problem.set_val(name, v)` and no `InputDefault`, gets the raw number `v` in every leaf with no conversion and no error (5 → 5 deg and 5 rad). OM3 rejects this at setup and asks for `set_input_defaults(units=...)` **Fixed on om4 `main` (PR #357). Verified: repro cases A–D all correct on `0787fcbf`.** | `ai/tools/repros/promoted_input_units_and_defaults.py`, case A. OAS hits it with ground effect: `alpha` is rad in `VortexMesh`, deg elsewhere | Every OAS group gives mixed-unit promoted inputs an `InputDefault` with units (case C converts correctly) |
| ✅ B-005 | **`InputDefault.val` is ignored.** With `input_defaults={"a": InputDefault(val=5.0, units="deg")}` and no `set_val`, each leaf keeps its own component default (0 and 1), and `get_val("a")` returns a leaf value rather than 5. The `units` part does work **Fixed on om4 `main` (PR #357). Verified: repro cases A–D all correct on `0787fcbf`.** | Same repro, case B | Components are also constructed with the intended default (e.g. `BsplineComp(cp_val=surface["twist_cp"])`), so the leaf default agrees with the `InputDefault` |
| ✅ B-006 | Ambiguous promoted-input defaults aren't diagnosed. Leaves promoted to one name with different default values (OAS: `alpha` 0 deg in `ConvertVelocity`, 1 deg in `EvalVelMtx`) are accepted silently, and the promoted value is taken from one of them. OM3 raises and asks for `set_input_defaults` **Fixed on om4 `main` (PR #357). Verified: repro cases A–D all correct on `0787fcbf`.** | Probe on `VLMStates`: `get_val("alpha")` = 1, `convert_velocity.alpha` = 0 before any `set_val` | Groups give these inputs explicit `InputDefault`s |
| 🟡 B-007 | **`compute_totals` reuses the of/wrt layout of its first call.** A later call with a different `wrt` list returns a matrix shaped for the first call, with stale columns (`wrt=[x, z]` then `wrt=[z]` gives `[[3, 3]]`, expected `[[3]]`) **Fixed in om4 `3c6068e9` on branch `compute_totals_layout_bug`, which is not on `main` (still reproduces on `0787fcbf`).** | `ai/tools/repros/compute_totals_reuses_first_layout.py` | Tests and cross-checks call `compute_totals` with one fixed of/wrt list per Problem and slice columns out of the result |
| ✅ B-008 | **Wrong total derivatives across mixed-unit promoted inputs.** `compute_totals` wrt a promoted input whose leaves declare different units seeds every leaf with 1, skipping the unit factor, in both fwd and rev. Values convert correctly (B-004 case C), so the model runs right while its gradients are wrong **Fixed on om4 `main` (PR #357). Verified: repro cases A–D all correct on `0787fcbf`.** | `ai/tools/repros/promoted_input_units_and_defaults.py`, case D: `d[c_deg.y, c_rad.y]/da` = `[1, 1]`, expected `[1, 0.01745]`. Found via OAS ground effect: d(CL)/d(alpha) off by 6–9× vs OM3 | `VortexMesh` now takes `alpha` in deg (converted internally), so every leaf of the promoted `alpha` shares units. Applies to any future mixed-unit fan-out too |
| B-009 | `DesignVar.units` isn't applied to total derivatives (TODO in `OptimizerVar.val`). Values convert to the DV's units, but derivatives stay per the promoted input's units, so a DV declared in different units gets mis-scaled gradients. Predates the B-008 fix | Reported by the om4 session while fixing B-004/B-008 | OAS design variables must use the same units as the promoted input they drive, until fixed |
| 🟡 B-010 | `ColoringSpec._failed` was sticky. One request whose total coloring wasn't worth using (e.g. an early small diagnostic `compute_totals`) disabled coloring for every later request, including the optimizer's. Signature: "Coloring will not be used" early in a run, then uncolored optimizer totals. **Fixed in om4 `3c6068e9` on branch `compute_totals_layout_bug`; not on `main`.** | Found by the om4 session while doing N-006 | none needed |
| B-011 | Latent: `JacobianPartition.nnz()` reads `sm._rows`, which no `Submat` defines, so it would raise `AttributeError` for any non-diagonal submat. Only the `"auto"` assembled-format path reaches it, and `DirectSolver.assembled_format` allows only `"dense"`/`"sparse"`, so it looks unreachable today | Reported by the om4 session during the B-003 audit | none needed |
