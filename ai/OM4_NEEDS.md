# om4 needs found while porting OpenAeroStruct

Running list of om4 components, features, and bugs that the OAS port ran into.
Each entry says what OAS does about it in the meantime. Strike through (`~~...~~`)
when resolved upstream; don't delete. ✅ = fixed on om4 `main`; 🟡 = fixed on an om4 branch that isn't on `main` yet (committed or not). Unmarked = still open.

**Last reassessed 2026-10-14 against om4 `main` @ `3e78ed96`** (B-003, B-004–B-008 repros rerun; B-009 re-probed; PRs #361, #363, #364 merged since the 2026-10-06 pass at `0787fcbf`), by rerunning every repro in `ai/tools/repros/` and the original probes against a clean worktree of that commit. Minimal reproductions live in `ai/tools/repros/`.

## Missing components / features

| ID | Need | Where OAS hit it | Interim in OAS |
|---|---|---|---|
| N-001 | `SplineComp` (at least `method="bsplines"`; OM3 also has akima, scipy methods) | `geometry/geometry_group.py`, structures groups (twist/chord/shear/thickness control points) | OAS-local `openaerostruct/utils/bspline_comp.py:BsplineComp`, a verbatim port of OM3's B-spline basis. Matches OM3 to round-off |
| N-002 | Per-subjac approximation (OM3 `declare_partials(of, wrt, method="cs"/"fd")`). `PartialsSpec` has no `method`; only a component-wide `differentiator` | ~16 components. Done so far: `aerodynamics/eval_mtx.py` (alpha), `aerodynamics/vortex_mesh.py` (alpha, height_agl, ground effect). Pending: `pg_scale.py`, `pg_wind_rotation.py`, `structures/fuel_vol.py`, … | **Decision (Robert, 2026-10-13): N-002 will not be addressed in om4. Each component gets a single differentiator.** A component is either fully analytic or fully `differentiator="cs"`/`"fd"`, never a mix. Components that were fully CS/FD in OM3 use `differentiator="cs"` (verified exact on a probe). Mixed components get hand-derived analytic partials for every pair, each cross-checked against OM3's CS values (`ai/tools/om3_crosscheck.py`) |
| N-003 | `assert_check_partials` and other testing asserts | every partials unit test | `openaerostruct/utils/testing.py:assert_check_partials` |
| ✅ N-004 | Per-component check settings (OM3 `set_check_partial_options(wrt, method, step)`) | ~17 components declare FD steps or CS for checking | **Fixed on om4 `main`: every component has `check_partials_options: CheckPartialsOptions` (`differentiator`, `use_coloring`, `probe_sparsity`); its `differentiator` overrides the one passed to `check_partials`.** It is per component, not per `wrt` as in OM3. OAS declares it as a class-level field default, e.g. `check_partials_options: om.CheckPartialsOptions \| None = om.CheckPartialsOptions(differentiator="cs")`. Done: `WaveDrag`, `ViscousDrag` (cs), `VLMMtxRHSComp` (fd, step 1e-5). Components whose OM3 setting was plain FD at the default step (`VLMGeometry`, `EvalVelMtx`) need nothing. Per-`wrt` ones (`pg_scale`, `pg_wind_rotation`, `length`) take the component-wide choice that fits all their inputs |
| N-005 | Subjacs are write-only inside `compute_partials`: `partials[of, wrt]` returns a `COOSubmat` that does not support slice assignment, in-place `+=`, or reads. OM3 code commonly fills a subjac piecewise (`partials[k][:n] = ...; partials[k][m:] += ...`) | 13 OAS modules, worst `geometry_mesh_transformations.py` (33 sites), `moment_coefficient.py` (25), `aerodynamics/geometry.py` (13) | Build the full value array locally and assign it once. Port rule 7 in `ai/ARCHITECTURE.md` |
| ✅ N-006 | Total coloring is computed once and isn't cached per of/wrt layout. Changing the request recomputes it, logging the misleading "Pre-computed coloring … is not compatible … will be computed dynamically" even though om4 computed it, not the user. An optimizer that interleaves a second request (e.g. a diagnostic `compute_totals`) recomputes coloring each time it switches. Options: key colorings by layout, or reword the warning **Fixed on om4 `main` (PR #361, `3c6068e9`): per-layout coloring cache, last 4 layouts.** | Reported by the om4 session while fixing B-007 | none needed yet; OAS doesn't use total coloring so far |
| N-007 | `ExecComp` has no diagonal-partials option (OM3 `has_diag_partials`). Vectorized ExecComps declare dense partials, so total and partial coloring can't help them | Reported by the om4 session while fixing B-007 | OAS uses few ExecComps; revisit when porting the ones in `integration/` |
| N-008 | `check_sparsity` (and so `SystemChecker`'s `sparsity` check) iterates only declared `(of, wrt)` keys, so it can't detect an entirely undeclared pair | Reported by the om4 session while doing B-001 | Full-mode `check_partials` (B-001) catches these |
| N-009 | **FD/CS fills allocate a dense `n_out × n_in` buffer per component**, even with a sparse declared pattern or partial coloring, both in normal linearization and in `check_partials` (measured by the om4 session: ~450 MB peak for N=3000 in both check modes). Large OAS components (e.g. `EvalVelMtx`, whose `vel_mtx`/`vectors` block is ~30,000 × 36,000 at realistic meshes, ~8.6 GB dense) can't be FD/CS-checked or FD-differentiated within reasonable memory. A column-streamed fill (one column at a time, scattered into the declared pattern or compared and discarded) would bound memory | Reported by the om4 session while measuring B-001 cost | OAS components with large inputs use analytic partials; their checks run on small meshes |
| N-010 | No directional (OM3-style dot-product) partials check. With the check now always full and uncolored, it costs one evaluation per input entry (plus one jvp per input entry and one vjp per output entry for matrix-free components), which is expensive for components with large inputs. A directional mode would be the cheap option there. Related: N-009 (dense FD buffer) | Raised by the om4 session as the natural follow-up to B-001/B-013 | Large OAS components are checked on small meshes |

## Bugs / behavior differences

| ID | Issue | Evidence | Interim in OAS |
|---|---|---|---|
| ✅ B-001 | `check_partials` built the FD/CS reference **only inside the declared sparsity pattern** (`compexecnode.py:436`, `subjacs = {n: sj.copy(zero=True) ...}`), so undeclared nonzeros and undeclared `(of, wrt)` pairs were invisible. OM3 compares against a dense approximation. **Fixed on om4 `main` (PR #364). Robert's decision: no option, `check_partials` always compares against a full uncolored reference over every `(of, wrt)` pair. Results gain `declared`, `missing` (undeclared entries violating tolerance) and `value_error`; `SystemChecker` reports undeclared nonzeros and wrong values separately. Matrix-free components are now checked too (see B-013). `CheckPartialsOptions.use_coloring` opts a component back into a declared-pattern-only check (N-004).** | Probe: `y = x**2 + x[0]` with only a diagonal declared; `Jref` showed zeros in column 0 below the diagonal | `utils/testing.py:assert_sparsity_complete` does a dense FD sweep for small explicit components; it is now redundant with om4's full check. Ports are also cross-checked against OM3's analytic Jacobians |
| ✅ B-002 | `get_tol_violation` returns `(0.0, 0.0, False)` for empty arrays, but callers unpack `(above_tol, max_abs, max_rel)`, so the order is wrong. Harmless today, since `0.0` is falsy **Fixed on om4 `main` (PR #364).** | `om4/utils/array_utils.py:541` | none |
| ✅ B-003 | **Duplicate `(row, col)` entries in a sparse pattern give wrong numbers outside the analytic matvec path.** First found as a false `check_partials` failure: the FD/CS reference counted a repeated coordinate once per listing (`Jref` 6 where 3 is correct). The om4 session's audit found the root cause in `COOSubmat` (`set_val_from_dense`, `set_col`, `set_row` wrote the full value into every listing) plus a second bug in `copy_to` (last listing wins). Real wrong answers: **CS as a component's differentiator** doubled totals (fwd and rev); FD did too under a sparse-assembled `DirectSolver`; partial coloring with FD/CS likewise; and **analytic partials under `DirectSolver(assembled_format="dense")`** were wrong (2.5 vs 4.2857 in a Newton/Direct cycle). Unaffected: matvec, `todense`, sparse assembly of analytic partials, group-level FD/CS, second-order checks, JAX/asdex. **Fixed on om4 `main` (PR #363, `40d5fceb`); fix confined to `om4/derivatives/submat.py`, tests in `om4/derivatives/tests/test_duplicate_partials.py`. Verified 2026-10-14: the repro reports `J` and `Jref` both `[3, 1, 1]`, fwd and rev totals correct.** | `ai/tools/repros/check_partials_duplicate_entries.py`: `J[0,0]=3` (correct), `Jref[0,0]=6`; fwd/rev totals both 3. Fixed branch prints `Jref` `[3, 1, 1]`, not reported wrong | **Correction:** an earlier version of this entry claimed OAS keeps duplicate patterns (`Stretch`, `Sweep`, `Dihedral`, …). A scan of all 28 ported components in 3 configurations (2026-10-06) found **no duplicate entries**, so OAS hasn't hit this. | ✅ B-004 | **Silent unit error.** An unconnected promoted input whose leaves declare different units, set with `Problem.set_val(name, v)` and no `InputDefault`, gets the raw number `v` in every leaf with no conversion and no error (5 → 5 deg and 5 rad). Verified: repro cases A–D all correct on `0787fcbf`.** | `ai/tools/repros/promoted_input_units_and_defaults.py`, case A. OAS hits it with ground effect: `alpha` is rad in `VortexMesh`, deg elsewhere | Every OAS group gives mixed-unit promoted inputs an `InputDefault` with units (case C converts correctly) |
| ✅ B-005 | **`InputDefault.val` is ignored.** With `input_defaults={"a": InputDefault(val=5.0, units="deg")}` and no `set_val`, each leaf keeps its own component default (0 and 1), and `get_val("a")` returns a leaf value rather than 5. Verified: repro cases A–D all correct on `0787fcbf`.** | Same repro, case B | Components are also constructed with the intended default (e.g. `BsplineComp(cp_val=surface["twist_cp"])`), so the leaf default agrees with the `InputDefault` |
| ✅ B-006 | Ambiguous promoted-input defaults aren't diagnosed.
