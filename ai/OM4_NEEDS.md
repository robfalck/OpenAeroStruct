# om4 needs found while porting OpenAeroStruct

Running list of om4 components, features, and bugs that the OAS port ran into.
Each entry says what OAS does about it in the meantime. Open items (still blocking
or still worked around) are listed first in each section; resolved ones move to
that section's "Resolved" table rather than being deleted, so the history stays.
✅ = fixed on om4 `main`; 🟡 = fixed on an om4 branch that isn't on `main` yet
(committed or not) — stays in the open table until it lands on `main`. Unmarked =
still open.

**Last reassessed 2026-10-20 against om4 `arch_udpate` @ `72bf3a7e`** (= upstream `main` @ `1a3c7947` plus one docs/API commit; 101 commits since the 2026-10-14 pass at `3e78ed96`, including PRs #370, #383, #386–#390, #392–#394). B-016's repro (`model_overrides_var_serialize.py`) was rerun and now passes; N-001, N-007, N-008 were checked by reading the new code/docs and, for N-001, by running the upstream test suite against a temporary worktree of the `metamodels` branch. Minimal reproductions live in `ai/tools/repros/`.

## Bugs / behavior differences

| ID | Issue | Evidence | Interim in OAS |
|---|---|---|---|
| B-015 | **Execution order of the graph varies from run to run.** With the default `collapse_by="cycle"`, the order of components in the root `GraphExecutionNode` (and so the XDSM and its tree) depends on `PYTHONHASHSEED`: on the 4x9 aerostructural benchmark `failure` precedes `liftdrag` in two seeds and follows it in another. Each order respects the data dependencies, so results shouldn't change; it only makes the displayed order, and anything keyed to position, unstable. **Low priority.** Likely cause: iteration over a `set` or `dict` built from hashed names when sorting the graph; sorting ties by declaration index would make it deterministic | Seen via the XDSM viewer (om4 `xdsm_tool` branch): `PYTHONHASHSEED=1 python ...` and `PYTHONHASHSEED=3 python ...` on `benchmark/bench_aerostruct.py` list the root's children in different orders. No repro script yet | none needed; outcomes are unaffected |
| B-017 | **`PETScDirectSolver`'s default (`sparse_solver_name=None`) is both slower and crash-prone compared to explicitly requesting `"klu"`.** With no `sparse_solver_name`, `pc.setFactorSolverType` is never called, so PETSc falls back to its own native LU, which raises `petsc4py.PETSc.Error: error code 73 ... Matrix is missing diagonal entries` on Jacobians (e.g. OAS's coupled aerostructural group) that don't explicitly store a diagonal entry in every row. The explicit `"klu"` backend not only avoids that crash but is the fastest serial option measured: ~6x faster than SciPy's `DirectSolver` (SuperLU) on the 4x41 aerostructural mesh's `compute_totals` (0.31s vs 1.84s); `"superlu"`/`"umfpack"` (PETSc-wrapped) are themselves dramatically *slower* than SciPy's own SuperLU for this problem. **Suggested fix: default `sparse_solver_name` to `"klu"` instead of `None`**, pending a check that the preference holds on a Jacobian with a structurally different (non-block-triangular-friendly) sparsity pattern than this benchmark's | `benchmark/bench_aerostruct.py --linear-solver petsc-klu` (and `petsc-superlu`/`petsc-umfpack`/`petsc-mumps` for comparison) on the 2x5/3x21/4x41 meshes; native-PETSc-LU crash reproduced by constructing `PETScDirectSolver` with `sparse_solver_name` left unset on the same model | `benchmark/bench_aerostruct.py`'s `LINEAR_SOLVERS["petsc-klu"]` passes `sparse_solver_name="klu"` explicitly; `LINEAR_SOLVERS` omits the native `"petsc"` type entirely for this reason |
