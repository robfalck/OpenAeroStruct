# Technical debt — OAS om4 port

Debt taken on deliberately during the port, and OAS features not yet ported. om4-side
gaps and bugs live in `ai/OM4_NEEDS.md`. Resolved entries are struck through and kept.

Severity: **High** = wrong results possible; **Medium** = will bite in a foreseeable next
step; **Low** = tidiness.

## Not yet ported

| ID | Item | Severity | Notes |
|---|---|---|---|
| ~~TD-001~~ | ~~Multi-section surfaces (`MultiSecGeometry`, `MultiSecAerostructGeometry`)~~ | Medium | **Resolved**: multi-section surfaces get their own `MultiSectionSurface` model (`openaerostruct/utils/surface.py`) rather than being shoehorned into `Surface`'s scalar fields, since per-section data is list-valued. `build_section_dicts`/`unify_mesh`/`multi_spline_join_kwargs` (`openaerostruct/geometry/multi_section.py`) replace OM3's `build_multi_spline`/`connect_multi_spline`: the "construction" join method (sections share control points) is now a declarative builder returning `{"subsystems": ..., "connections": ...}` for the caller to merge into its own `om.Group`, instead of OM3's imperative post-setup `prob.model.connect(..., src_indices=...)`, which has no om4 equivalent. The "constraint" join method (`GeomMultiJoin`) was already ported/unit-tested. All 5 `test_multi_*.py` integration tests are ported and pass. One finding along the way: SLSQP's `Constraint(equals=0.0)` on `GeomMultiJoin`'s `section_separation` crashes with "Singular matrix C in LSQ subproblem" because that output's Jacobian is exactly rank-deficient for straight/untapered wings; reproduced identically against OM3's own `ScipyOptimizeDriver`, so it's a genuine scipy SLSQP limitation, not an om4 gap — worked around in the affected tests with a tight tolerance band (`Constraint(lower=-1e-6, upper=1e-6)`) instead of true equality. The four `docs/advanced_features/scripts/basic_2_sec*.py` example scripts remain unported pending wider doc-script porting (tracked under TD-004/TD-005, not a new TD id) |
| TD-002 | Compressible VLM (`CompressibleVLMStates`, `pg_scale.py`, `pg_wind_rotation.py`) | Medium | `AeroPoint(compressible=True)` raises. `pg_*` also need analytic partials for the Mach/alpha/beta columns OM3 complex-stepped (single differentiator per component, OM4_NEEDS N-002) |
| TD-003 | FFD geometry (`ffd_component.py`, `DVGeo` option) | Low | `DVGeo` is a live pygeo object and can't be a serializable field. Needs a design for referencing external geometry engines |
| TD-004 | `mphys/` | Low | mphys is built on OM3 |
| TD-005 | `plot_wing` / `plot_wingbox` | Low | Need optimizer-iteration recording, which om4 lacks |
| ~~TD-006~~ | ~~Aerostructural integration tests (the groups `AerostructGeometry`, `CoupledAS`, `CoupledPerformance`, `AerostructPoint` are ported; only `test_aerostruct_analysis.py` is)~~ | Medium | **Resolved**: all in-scope files (`test_aerostruct*`, `test_v1_aerostruct_*`, `test_wingbox_derivs/distributed_fuel`, `test_multipoint_wingbox_*`, `test_morphing_aerostruct`, `test_scaneagle`, `test_simple_rect_AS`) are ported to om4's declarative API. `test_multipoint_parallel.py` is ported but **blocked on OM4_NEEDS B-020** (its `AerostructGeometry` wing, built as a `Problem`-model sibling of the test's `parallel=True` `om.Group`, hits a false "already exists in OrderedVars" `RuntimeError` under real `mpirun -n 2`, not reproducible under `-n 1`); it cannot pass until that's fixed upstream. Tests blocked by TD-001/TD-002/TD-003/TD-004 remain out of scope |

## Deliberate deviations from OM3

| ID | Deviation | Severity | Why / follow-up |
|---|---|---|---|
| ~~TD-102~~ | ~~`Geometry` passes control-point values into `BsplineComp(cp_val=...)` as well as `input_defaults`~~ | Low | **Resolved**: OM4_NEEDS B-005 (`InputDefault.val` ignored) is fixed on om4 `main`, and `Geometry`/`TubeGroup` now build `om4.api.SplineComp` (OM4_NEEDS N-001) instead of the local `BsplineComp`. `SplineSpec.control_val` is just the component's own field, so passing it alongside `input_defaults` is no longer a workaround, it's just giving the component a sensible default |
| TD-103 | Spline outputs and control-point inputs are 1-D `(n,)` rather than OM3's `(1, n)` | Low | ADL-004. Scripts that index `twist[0, :]` need updating. om4's `SplineComp` natively outputs `(vec_size, n_interp)` (matching OM3's `(1, n)` with `vec_size=1`), but OAS still promotes it directly to a 1-D consumer shape with no reshape step: `(1, n)` and `(n,)` are connection-compatible in om4 (`om4/utils/array_utils.py:array_connection_compatible` strips size-1 axes before comparing), so the promotion "just works". The `twist[0, :]` caveat above still doesn't apply. The control-point *input* side has no sibling leaf to borrow a 1-D shape from, so `openaerostruct/utils/om4_utils.py:spline_or_broadcast` (OM4_NEEDS N-011) gives it one explicitly: a 1-D passthrough `ExecComp` promoted under the control-point name, connected into the spline's 2-D input |
| TD-104 | `set_check_partial_options(wrt=...)` becomes a component-wide `check_partials_options` | Low | OM4_NEEDS N-004. The check differentiator is chosen per component, not per `wrt`, so a component with one FD-only input is checked with FD for all of them |
| TD-105 | `VLMMtxRHSComp` and `MomentCoefficient` recompute in `compute_partials` what OM3 cached from `compute` | Low | Removes a call-order dependence. Costs one extra assembly per linearization; measure if it shows up in profiles |
| TD-106 | Structures leaf changes beyond a mechanical port: `StructureWeightLoads.element_lengths` is computed (OM3 left it unset), `WingboxFuelVolDelta` no longer mutates its inputs, `Length` uses the complex-safe `norm`, `CreateRHS` allocates a complex-safe buffer | Low | Needed for complex-step and om4's read-only inputs; values are unchanged |
| TD-107 | `AerostructPoint` keeps OM3's wiring in which `load_factor` is promoted from each `CoupledAS` into `coupled` but not out of it, so the coupled structure sees its default `load_factor`, not the one given to `total_perf` | Medium | Reproduced for parity from reading the code, not yet verified at runtime. Check whether it is a latent OM3 bug (matters when `load_factor != 1` with weight relief, fuel or point masses) |
| TD-108 | Tolerances for `check_partials` on CS-differentiated components (vonmises, fuel_loads, wingbox) are loosened in integration tests (`atol=1e-1, rtol=1e-4`) | Low | om4 switches the reference to 4th-order central FD when the component differentiator is complex step, which is noisy for large Jacobians. Consider an OM4_NEEDS entry if this keeps recurring |
| TD-109 | `test_add_point_masses.test_simple_values` is skipped | Low | Reference values assume g=9.8, `grav_constant` is 9.80665; it was already skipped upstream |
| TD-110 | `AerostructPoint` has `input_defaults` for `alpha`, `beta`, `v`, `rho`, `Mach_number` | Low | Leaves disagree on defaults and om4 rejects ambiguous promoted inputs; the values are placeholders overridden by `set_val` |
